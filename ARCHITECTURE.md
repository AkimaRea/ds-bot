# Архитектура проекта Discord-бота

Документ описывает целевую архитектуру локально хостимого Discord-бота для пошаговой стратегии из `TECHNICAL_SPEC.md`.

## 1. Цели архитектуры

- Разделить Discord-интерфейс и игровую механику.
- Сохранять состояние между перезапусками локального процесса.
- Защититься от повторной обработки хода и повторных нажатий кнопок.
- Сделать правила игры тестируемыми без подключения к Discord.
- Оставить путь к будущему переходу с SQLite на PostgreSQL без переписывания доменной логики.

## 2. Рекомендуемый стек

Базовый стек для локального хостинга:

- Python 3.12+.
- `discord.py` 2.x для slash/text-команд, кнопок и взаимодействия с каналами.
- SQLite как локальная база данных.
- SQLAlchemy 2.x как слой доступа к данным.
- Alembic для миграций схемы.
- Pydantic или dataclasses для DTO и валидации входных данных.
- `pytest` для тестов игрового движка.
- `python-dotenv` для локальной конфигурации.
- `structlog` или стандартный `logging` для файловых логов.

SQLite выбран как основной вариант, потому что бот будет хоститься локально. Для одной игры, одного Discord-сервера и пошаговой обработки через ведущего этого достаточно.

## 3. Высокоуровневая схема

```text
Discord Server
    |
    | commands, buttons, channel messages
    v
Discord Adapter
    |
    | parsed commands / button events
    v
Application Services
    |
    | transactions, permissions, orchestration
    v
Game Engine
    |
    | deterministic game rules
    v
Repositories
    |
    v
SQLite database
```

Главное правило: `Game Engine` не знает о Discord, ролях, каналах и сообщениях. Он принимает состояние и приказы, возвращает новое состояние, события хода и ошибки правил.

## 4. Модули проекта

Рекомендуемая структура:

```text
ds-bot/
  src/
    ds_bot/
      main.py
      config.py
      logging.py

      discord/
        bot.py
        commands.py
        buttons.py
        permissions.py
        presenters.py
        channel_resolver.py

      application/
        game_service.py
        order_service.py
        turn_service.py
        status_service.py
        setup_service.py

      domain/
        models.py
        enums.py
        orders.py
        errors.py
        rules.py
        engine.py
        initial_map.py
        status.py

      persistence/
        db.py
        models.py
        repositories.py
        unit_of_work.py
        migrations/

      tests/
        domain/

```

Ответственность слоев:

- `discord`: принимает события Discord, проверяет базовый контекст канала/пользователя, отправляет ответы и статусы.
- `application`: управляет сценариями: начало игры, ввод приказа, фиксация приказа, конец хода.
- `domain`: содержит правила игры, расчеты, валидацию приказов, обработку хода.
- `persistence`: хранит и загружает состояние, выполняет транзакции.

## 5. Доменная модель

Основные сущности:

- `Game`: глобальное состояние игры.
- `City`: город, владелец, уровень замка, юниты.
- `Team`: команда, Discord-роль, Discord-канал, статус фиксации приказа.
- `Order`: приказ текущего хода.
- `TurnHistory`: обработанный ход и события.
- `BattleHistory`: результат боя по конкретному городу.
- `UnitReservation`: зарезервированные юниты по городу и приказу.

Ключевые enum-типы:

- `GameStatus`: `not_started`, `active`, `finished`.
- `OwnerType`: `team`, `barbarians`, `zombies`, `empty`.
- `OrderType`: `attack`, `move`, `donate`, `upgrade`.
- `TurnPhase`: `movement`, `donation`, `upgrade`, `attack`, `income`, `zombie_growth`.

## 6. Потоки выполнения

### 6.1. Начало игры

1. Ведущий нажимает кнопку `Начало игры`.
2. `Discord Adapter` проверяет канал и права ведущего.
3. `SetupService` открывает транзакцию.
4. Текущее состояние сбрасывается.
5. Создаются стартовые города, команды, зомби-город, варвары и пустые города.
6. Ход устанавливается в `1`, статус игры становится `active`.
7. Ведущему публикуется полный статус.
8. Каждой команде публикуется приватный статус.

### 6.2. Ввод приказа

1. Игрок вводит `!attack`, `!move`, `!donate` или `!up`.
2. `commands.py` парсит текст в DTO приказа.
3. `permissions.py` определяет команду по роли и каналу.
4. `OrderService` вызывает доменную валидацию.
5. Домен проверяет игру, владельцев городов, лимиты, резервы и статус фиксации.
6. При успехе создается `Order` и `UnitReservation`.
7. Бот подтверждает сохранение приказа или возвращает понятную ошибку.

### 6.3. Отправить приказ

1. Игрок нажимает кнопку `Отправить приказ`.
2. Проверяются роль, канал и принадлежность к команде.
3. У команды ставится `orders_locked = true`.
4. Новые приказы этой команды до следующего хода отклоняются.

### 6.4. Конец хода

1. Ведущий нажимает кнопку `Конец хода`.
2. `TurnService` берет блокировку обработки хода.
3. В одной транзакции загружается состояние и приказы текущего хода.
4. `GameEngine.process_turn()` применяет фазы строго по ТЗ:
   1. Перемещения.
   2. Донаты.
   3. Улучшения замков.
   4. Атаки.
   5. Доход от замков.
   6. Рост армии зомби.
5. Сохраняются новое состояние, история хода и история боев.
6. Очищаются приказы, резервы, лимиты донатов и фиксации команд.
7. Если обработан 6-й ход, игра переводится в `finished`; иначе номер хода увеличивается.
8. Публикуются статусы ведущему и командам.

## 7. Обработка боя

Атаки группируются по `target_city_id`, затем внутри цели по `team_id`.

Алгоритм:

1. Собрать суммарный вклад каждой команды.
2. Вычесть атакующие юниты из городов отправления.
3. Сравнить общую атаку с защитой города.
4. Если атака меньше защиты, город остается владельцу, защита уменьшается.
5. Если атака равна защите, город остается владельцу, юниты города становятся `0`.
6. Если атака больше защиты, город получает команда с максимальным вкладом.
7. При равном максимальном вкладе выбрать победителя случайно.
8. Для воспроизводимости сохранить `random_seed` или выбранного победителя в истории боя.
9. Количество погибших за ход считать только по результатам боев.

Важно: случайный выбор владельца должен происходить внутри движка, а результат должен записываться в `battle_history`, чтобы после перезапуска не было другого исхода.

## 8. Схема SQLite

Минимальная схема:

```text

teams

  discord_channel_id

  donated_units_this_turn

cities
  id
  game_id
  owner_type
  owner_team_id
  castle_level
  units

orders
  id
  game_id
  turn_number
  team_id
  type
  source_city_id
  target_city_id
  units
  upgrade_cost
  created_at

unit_reservations
  id
  game_id
  turn_number
  team_id
  city_id
  order_id
  units

turn_history
  id
  game_id
  turn_number
  killed_units
  events_json
  processed_at

battle_history
  id
  game_id
  turn_number
  target_city_id
  defender_owner_type
  defender_team_id
  defender_units
  attackers_json
  winner_owner_type
  winner_team_id
  remaining_units
  killed_units
  random_seed

message_refs
  id
  game_id
  kind
  team_id
  channel_id
  message_id
```

Индексы:

- `orders(game_id, turn_number, team_id)`.
- `unit_reservations(game_id, turn_number, city_id)`.
- `turn_history(game_id, turn_number)` с уникальностью.
- `teams(game_id, discord_channel_id)`.
- `teams(game_id, discord_role_id)`.

`message_refs` нужен, если бот будет редактировать существующие статусные сообщения вместо постоянной публикации новых.

## 9. Транзакции и защита от повторов

Для локального SQLite достаточно строгой дисциплины транзакций:

- Все изменения при обработке хода выполняются в одной транзакции.
- Перед обработкой ставится `games.processing_turn = true`.
- `turn_history(game_id, turn_number)` имеет уникальный индекс.
- Повторное нажатие `Конец хода` при `processing_turn = true` отклоняется.
- После успешной обработки флаг сбрасывается.
- При аварийном падении на старте бот проверяет зависший `processing_turn` и сообщает ведущему.

Для кнопок Discord:

- custom id должен включать действие, `game_id`, `turn_number`, опционально `team_id`.
- обработчик сверяет `turn_number` кнопки с текущим ходом;
- устаревшие кнопки отвечают ошибкой без изменения состояния.

## 10. Конфигурация локального запуска

Файл `.env`:

```text
DISCORD_TOKEN=
DISCORD_GUILD_ID=
HOST_ROLE_ID=
CONTROL_CHANNEL_ID=
ZOMBIE_CHANNEL_ID=
DATABASE_URL=sqlite:///./data/ds_bot.sqlite3
LOG_LEVEL=INFO
```

Локальная структура данных:

```text
data/
  ds_bot.sqlite3
logs/
  bot.log
```

Запуск для разработки:

```text
python -m ds_bot.main
```

Запуск как локальный сервис на Windows:

- создать виртуальное окружение в папке проекта;
- настроить `.env`;
- добавить запуск `python -m ds_bot.main` в Task Scheduler;
- выставить Restart on failure;
- хранить `data/` и `logs/` рядом с проектом или в отдельной локальной папке.

Альтернатива для изоляции:

- Docker Compose с одним сервисом бота;
- volume для `data/` и `logs/`;
- без отдельного контейнера базы, потому что SQLite хранится файлом.

## 11. Discord-интерфейс

Минимальная версия:

- текстовые команды с префиксом `!`, потому что они прямо описаны в ТЗ;
- кнопки `Начало игры`, `Конец хода`, `Отправить приказ`;
- проверка ролей и каналов на каждое действие.

Расширяемая версия:

- добавить slash-команды как более удобную альтернативу;
- оставить текстовые команды для совместимости с ТЗ;
- использовать ephemeral-ответы для ошибок, если команда пришла через interaction.

Статусы:

- ведущий получает полную карту;
- команды получают только свои города;
- зомби-канал получает статус города `0`;
- форматирование статусов находится в `discord/presenters.py`, а не в движке.

## 12. Тестирование

Обязательные тесты домена:

- стартовая карта создается по ТЗ;
- резерв не позволяет потратить больше свободных юнитов;
- фиксация приказа запрещает новые приказы;
- порядок фаз хода соответствует ТЗ;
- донат влияет на защиту до атаки;
- улучшение списывает стоимость и повышает доход;
- несколько атак одной команды суммируются;
- несколько команд на один город выбирают победителя по вкладу;
- равный вклад сохраняет выбранного случайного победителя в истории;
- зомби получает `floor(killed_units / 2)`;
- после 6-го хода игра завершается;
- повторная обработка одного хода невозможна.

Интеграционные тесты:

- сервис начала игры создает состояние в SQLite;
- сервис конца хода сохраняет `turn_history`;
- ошибки прав не меняют состояние.

Discord-слой лучше покрывать точечно моками, а основную уверенность держать в тестах `domain` и `application`.

## 13. План реализации

1. Создать каркас проекта, конфиг, логирование и подключение SQLite.
2. Описать доменные модели, enum-типы и стартовую карту.
3. Реализовать репозитории и миграции.
4. Реализовать валидатор приказов и резерв юнитов.
5. Реализовать игровой движок обработки хода.
6. Покрыть движок unit-тестами.
7. Подключить Discord-команды.
8. Подключить Discord-кнопки.
9. Реализовать публикацию статусов.
10. Добавить защиту от повторной обработки и файловое логирование.
11. Подготовить локальный запуск через `.env` и инструкцию.

## 14. Открытые решения

Для первой версии предлагается зафиксировать следующие решения:

- использовать SQLite;
- поддерживать текстовые команды `!attack`, `!move`, `!donate`, `!up`;
- роли и каналы команд задавать через конфиг или команду ведущего в будущем;
- зомби-панель в первой версии только показывает состояние города `0`;
- ведущий не редактирует состояние вручную, пока это не появится в отдельном ТЗ;
- публичные анонсы и экспорт истории оставить на следующий этап.
